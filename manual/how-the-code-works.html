How OxBox works

1. The system at a glance

OxBox is one ASP.NET Core server. It drives the box's hardware, shows the box's screen, serves the admin web app and sends alerts, all from the same process. The box itself contains an OX Point BU, a control unit with the barcode reader, the locks and the lamps. The BU is a WebSocket server, and OxBox connects to it as a client.

Startup is in Program.cs: it registers the layers, then creates or migrates the database, seeds demo accounts and data, and starts two background services, the BoxSupervisor and the OutboxDispatcher.

2. The five projects

The solution is split by what each part may know. The protocol knows only JSON. The domain knows only cylinders and boxes. The application knows the business processes but not how the hardware or the database is reached. Infrastructure and Web supply those.

The build enforces this: Domain and Application reference no infrastructure packages, warnings are errors, and the coding standards in docs/development.md apply everywhere.

3. One agent per box

BoxSupervisor (Infrastructure) is a background service. At startup it loads every box from the database, retrying every 10 s while the database is unavailable, and starts one BoxAgent for each. When a box is added or its BU address changes in the web app, the admin page calls IBoxAgents.StartOrRestartAsync and the supervisor replaces that box's agent.

The agent is the box's single owner. Its key idea is one queue, one reader: everything that can happen at the box is put on the same queue and handled strictly one event at a time.

Each event gets its own dependency-injection scope, so every workflow, the IBoxStore and its EF Core context live exactly as long as one event. The agent also builds three helpers once per run and passes them to every workflow inside a BoxLink:

  • BoxHardware opens a position (with retries) and pulses a lamp relay;
  • BoxSignals shows a screen on the display and lights the green or red lamp;
  • BoxLink.Visit holds the technician's visit in progress, in memory only.

4. What a scan turns into

The box has one barcode reader for everyone. BoxEvents.ScannedAsync first asks whether the code belongs to an active technician, then routes on two facts:

After the workflow, unless a visit is open, the stock alerts are re-evaluated and everything is saved (section 9).

5. The exchange, step by step

This is the main process: a department brings an empty cylinder and leaves with a full one. First the pure function ExchangeRules.Decide checks the scan in the order the client's request lists them. The first check that fails becomes the error shown on the display:

  1. The barcode is registered and active, otherwise UnknownBarcode.
  2. The cylinder is not already in a box, otherwise AlreadyReturned.
  3. It is recorded as being at its department, otherwise NotAtCostCentre.
  4. The box holds a full cylinder of the same department, otherwise NoFullCylinderForCostCentre.
  5. A slot is free for the empty one, otherwise NoFreePosition.

The lowest-numbered free slot and the lowest-numbered matching full cylinder are chosen, so staff can predict which doors will open. Then the workflow opens the locks:

Every movement goes through CylinderLedger, which changes the cylinder through the domain and adds a CylinderTransaction with the full or empty flag configured at that moment. The dispense transactions are what the hospital invoices.

6. Talking to the BU

BuConnection keeps the WebSocket open and reconnects with growing delays when it drops. The awkward part of the OX Point protocol is that replies carry no request ID. A reply can only be matched to its command by content, so the connection allows only one command in flight and checks every incoming message against it:

The JSON shapes live in OxBox.OxPointProtocol. Every key and fixed value is defined once in WireNames, which the parsers and writers in both directions share. The simulator in tools/OxBox.BuSimulator uses the same protocol project, so it cannot drift from the server's view of the wire format.

7. A cylinder's life

A cylinder keeps its barcode and its department for life. Its location and status change only through four intent-named methods on Cylinder. Each method checks that the move is allowed (it throws otherwise) and returns the audit record of the change:

The workflows check the same conditions first (ExchangeRules, ServiceRules) and turn them into friendly errors. So an exception from Cylinder means a bug, never a user mistake. A cylinder in a box cannot be deactivated, so the box never holds a cylinder it is not allowed to hand out.

8. Service visits

A technician restocks the box with their personal service code. The visit is held in memory in BoxLink.Visit. If the server restarts, the visit simply ends; every movement it made is already saved.

If an empty cylinder's slot fails to open at the start, that cylinder stays recorded in the box and is collected on a later visit. A rejected insert (unknown code, already in a box, still at a department, box full) shows an error and then returns to the service screen.

9. Stock alerts and the outbox

After every event outside a service visit, StockAlertEvaluator counts the full cylinders per department in the box and works out which alert should be active. It compares that with the alerts that are active, and raises or resolves the difference. So it corrects itself even if an earlier evaluation was missed, for example after a crash.

Recipients come from the Alerts page: some receive alerts for every department, others for one. A department can override the default low-stock threshold on the Cost centres page. The dispatcher holds no database transaction while it sends, so a slow mail server never holds up the box agents.

10. The box display

The workflows never produce text. They say which screen to show (ReadyScreen, ExchangeOpenScreen(8, 1), RejectedScreen(UnknownBarcode) and so on), and the web layer turns that into words in the right language.

All wording is in Resources/Kiosk/KioskTexts.resx (Czech) and KioskTexts.en.resx (English), keyed by screen and error name. Adding a language means adding a resource file, not touching any workflow.

11. The admin web app

The admin app is made of Blazor Server pages in Components/Pages/Admin. They read the database directly through an EF Core context factory and do not go through the box agents. They are the "back office": registering cylinders, technicians and recipients, viewing transactions, and exporting reports (ReportQueries, CSV through AdminEndpoints).

UserScope turns the signed-in user into "is admin" plus "which departments may be shown", and each page filters with MaySee. The live connection state on the dashboard comes from BoxStatusBoard, an in-memory map that the agents update.
